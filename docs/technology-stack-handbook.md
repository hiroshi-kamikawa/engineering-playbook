# 技術構成ハンドブック

小規模〜中規模のWebサイトやWebアプリを、AIと協働して素早く作り、長く運用するための標準方針。目的は「最先端の部品を並べること」ではなく、要件に対して十分な構成を、少ない判断と運用負荷で選ぶこと。

> この文書は初期値（default）を定める。要件が初期値を上回るときだけ、例外を明示して構成を変更する。

設計思想を一行にすると、**Cloudflareはcompute、Clerkはidentity、DBはbusiness data。それ以外は必要になるまで増やさない**。

## 1. 基本思想

### AIバイブコーディングを前提にする

AIに実装を依頼するほど、構成と責務の境界は明示的である方がよい。フレームワークやサービスを増やすほど、AIが読むべき規約・設定・接続点も増える。

- まず動く最小構成を作り、機能単位で積み上げる
- 役割が重なるライブラリを同時に採用しない
- 採用理由、非採用条件、データの所有者をREADMEやこの文書に残す
- 「将来使うかもしれない」ものは、必要になってから導入する
- AIへの指示では、技術名だけでなく、対象（公開サイトかアプリか）、認証の有無、DB要件を明示する

### 軽量・運用最小

サーバー、認証、メール、DBを自前運用する範囲を絞り、マネージドサービスに任せられる部分は任せる。ただし、サービスを増やすこと自体が軽量化ではない。設定・課金・障害時の切り分けまで含めた総量で判断する。

### 明示性を優先する

魔法の自動化や暗黙の連携より、通常のHTTP、通常のSQL、単純な環境変数、明確なディレクトリ構成を優先する。DBや認証の境界は、コード上でも言葉でも一貫させる。

### boring technology（退屈な技術）

技術的に目新しいかではなく、資料が多く、採用例があり、交換や撤退の判断がしやすいかを重視する。新しい技術を禁止するのではなく、導入する場合は「何が解決され、どの複雑さが増えるか」を一文で説明できる状態にする。

## 2. 標準構成

### 構成の選択ルール

| 用途 | 標準構成 | 判断の要点 |
| --- | --- | --- |
| 公開サイト・SEO重視・ログイン不要 | Astro | 静的生成やサーバー生成を中心に、初期HTML・SEO・OGPを優先 |
| ログインありWebアプリ・SaaS・管理画面 | Vite + React + Hono + Clerk + Drizzle + Cloudflare Workers | SPA中心のUIとAPIを分離し、認証と実行基盤をマネージドに寄せる |
| リレーショナルDB（初期候補） | Cloudflare D1 | 単純CRUD、低〜中規模、Cloudflare内で完結したい場合 |
| PostgreSQL | Neon | Postgres固有機能、複雑なトランザクション、高い同時書き込みなどの要件が明確な場合 |
| メール | Resend | トランザクションメールを実際に送る必要が出た時だけ |

### アプリ構成の責務

```text
ブラウザ
  └─ Vite + React（画面、状態、入力）
       └─ Hono（HTTP API、認可、ユースケース）
            └─ Drizzle（スキーマ、クエリ、マイグレーション）
                 └─ D1 または Neon（永続データ）

認証・セッション: Clerk
実行基盤・配信: Cloudflare Workers
メール送信: Resend（必要時のみ）
```

Clerkは認証・アイデンティティ・セッションを担当する。アプリ固有の権限、チーム、契約、業務データはアプリDBで管理し、ClerkのIDと自前のユーザー・組織レコードの対応を明示する。

Honoはごく小さなAPIなら省略できるが、標準構成には残す。薄い依存でルーティング、ミドルウェア、入力検証、認可、エラー処理の置き場所が定まり、AIが実装先を迷いにくくなるため。

## 3. D1 vs Neon

D1とNeonは、Drizzleで扱えても同じDBではない。D1はSQLite系、NeonはPostgreSQLであり、SQL方言、ロック、トランザクション、型、拡張、同時書き込みの特性が異なる。「後で無痛移行できる」前提では設計しない。

### D1を選ぶ

- CRUD中心でデータモデルが素直
- 読み取り中心、または書き込み競合が限定的
- Cloudflare Workersと同じ運用面に寄せたい
- SQLite互換で十分で、Postgres固有機能を使わない
- 小さく始め、インフラ運用を最小化したい

### Neonを選ぶ

- PostgreSQLの型、拡張、全文検索、JSON操作などを明確に使う
- 複雑なJOIN、整合性制約、トランザクション境界が重要
- 同じDBへの高い同時書き込みが見込まれる
- 既存DB・分析基盤・外部ツールがPostgres前提
- チームのSQLや運用知識がPostgres中心

### 選択時の実務ルール

1. DB固有機能を使う予定がなければ、D1から始める。
2. 「Postgresが必要な理由」を機能名で説明できるなら、最初からNeonにする。
3. D1/Neon両対応を目的にクエリを不自然に制限しない。DBはプロジェクト単位で決める。
4. 迷う場合は、最初にデータモデルと代表クエリを書き、同時書き込み・トランザクション・検索要件を確認する。

## 4. TanStack Startを使う条件

通常は「公開SEOサイト＝Astro」「ログインありアプリ＝Vite + React + Hono」の二択で十分。TanStack Startは、次の条件が複数重なる場合に採用候補とする。

- Reactで公開ページとログイン後アプリを一つのフルスタック構成に統一したい
- SSR、ルーティング、データローディング、サーバー機能をReact中心で統合したい
- 公開ページにもインタラクションが多く、Astroの境界をまたぐコストが大きい
- チームがTanStackのルーティング・サーバー実行モデルを理解し、継続運用できる

SEOが必要という一点だけで採用しない。SEOのみならAstro、ログイン後中心ならVite + React + Honoをまず検討する。

## 5. Hyperdriveを最初から入れない理由と採用条件

Hyperdriveは、Workersから外部Postgresへ標準的なPostgres接続でアクセスする際の接続プールや経路最適化に意味がある。一方、D1を使う構成では対象がない。Neonはserverless driverで直接接続できるため、小規模アプリではまずその単純な経路から始められる。

最初から入れない理由は、接続経路・設定・障害切り分けを増やす割に、要件がなければ価値が出ないから。NeonとHyperdriveを重ねると、障害時にWorker、Hyperdrive、Neon、Postgres queryのどこが原因かを見る必要がある。Neonを採用しただけで自動的に追加しない。

次のような状況で導入を検討する。

- 標準的なPostgres driverや既存の外部PostgresをWorkersから使う
- リクエスト増加に伴い接続数やレイテンシーが問題になった
- 既存DBを維持したままWorkersへ移行する必要がある
- 1リクエスト内のDB往復が多く、接続再利用やDB近接配置の効果が見込める
- 負荷試験や実測で、接続管理がボトルネックと確認できた

導入前に、DB接続エラー、接続数、クエリ時間、リージョン間レイテンシーを観測できるようにする。推測だけで追加しない。導入する場合も、transaction poolingによるセッション機能の制約を確認する。read-after-writeの鮮度が必要なCRUDではquery cacheを初期状態で無効にし、キャッシュ可能な読み取りだけを後から明示的に分ける。

## 6. Better Auth vs Clerk

| 観点 | Clerk | Better Auth |
| --- | --- | --- |
| 位置づけ | 認証を外部サービスに委譲 | アプリ側で認証を構成するライブラリ |
| 運用 | UI・セッション・各種認証機能を任せやすい | DB、メール、セッション等の運用責任が増える |
| 初期実装 | 速い。標準的なログイン要件に向く | 要件に合わせて細かく制御しやすい |
| 依存 | ベンダー依存、料金・仕様変更の影響 | 自前実装・保守への依存 |
| 向くケース | AIで素早くSaaSを作り、認証運用を減らしたい | データ所在、UI、認証フローを自分で管理したい |

標準はClerk。認証基盤を自前管理する理由が具体的にある場合だけBetter Authを選ぶ。どちらでも、認証（本人確認）と認可（アプリ内の権限）を分離する。組織、ロール、購読状態などを認証サービスの設定だけで表現しない。

## 7. Resend導入条件

Resendは「メールを送る機能」が要件になった時に追加する。ログイン不要の公開サイトや、アプリ内通知だけの段階では不要。

導入する条件の例:

- ウェルカムメール、プロダクト通知、レポート配信が必要
- アプリが管理する招待、領収書、操作完了・失敗通知が必要
- 送信元ドメイン、テンプレート、配信失敗の扱いを管理する必要がある

導入時は、送信処理をアプリのユースケースから分離し、送信失敗時の再試行・重複送信・個人情報のログ出力を決める。Clerkを使う場合、メール確認やパスワードリセットなどの認証メールはまずClerkに任せる。Clerkの標準メールで要件を満たすなら、別途Resendを追加しない。

## 8. 避けたい過剰設計

- 公開SEOページに、必要のないReact SPAを載せる
- 小規模CRUDに、複数DB・キャッシュ・キュー・検索基盤を同時に入れる
- D1とNeonを抽象化しすぎて、両方の最低公約数だけで設計する
- 認証サービス、メールサービス、権限サービスを別々に導入し、同期処理を増やす
- 実測なしにHyperdrive、Redis、専用オブザーバビリティ基盤を追加する
- 将来のマイクロサービス化を理由に、最初からサービス境界とリポジトリを分割する
- UIフレームワークを複数併用し、同じ責務を複数のライブラリで解決する
- 「念のため」の環境、機能フラグ、設定項目を増やす

複雑さが必要になったら、先に要件・計測結果・運用上の痛みを記録し、一度に一つだけ追加する。

## 9. 構成を帰着させるチートシート

### Yes/No質問フロー

```text
Q1. 主目的は公開ページのSEO・初期表示・OGPか？
  Yes → Astro。Q2以降は、別途アプリ部分がある場合だけ続ける。
  No  → Q2へ。

Q2. ログイン、個人データ、業務操作があるか？
  No  → Astroまたは静的サイト構成。不要なAPI・認証を足さない。
  Yes → Vite + React + Hono + Clerk + Drizzle + Workersを基本にする。

Q3. Reactで公開ページとアプリを一つに統合する強い理由があるか？
  Yes → SSR等の要件も確認し、TanStack Startを検討。
  No  → 公開はAstro、アプリはVite + React + Honoに分ける。

Q4. Postgres固有機能、複雑なトランザクション、高い同時書き込みが明確に必要か？
  Yes → Neon。
  No  → D1。

Q5. メールをアプリから送る要件があるか？
  Yes → Resend（Clerk標準メールで足りるか先に確認）。
  No  → Resendなし。

Q6. 外部DB接続の接続数・遅延が実測で問題か？
  Yes → Hyperdriveを検討し、負荷試験で確認。
  No  → D1、またはNeon serverless driverの単純な経路を維持。

Q7. 認証基盤を自前管理する具体的な理由があるか？
  Yes → Better Authを検討。
  No  → Clerk。
```

### 決定表

| 質問 | Yesなら | Noなら |
| --- | --- | --- |
| SEO重視の公開サイトか | Astro | 次へ |
| ログインありのアプリか | Vite + React + Hono | Astro/静的構成 |
| React統合SSRが必須か | TanStack Startを検討 | 二つの標準構成を分離 |
| Postgres固有要件があるか | Neon | D1 |
| アプリ送信メールが必要か | Resendを検討 | 導入しない |
| 外部DB接続の実測課題があるか | Hyperdriveを検討 | 導入しない |
| 認証を自前管理する必要があるか | Better Authを検討 | Clerk |

### AIに渡す構成指定テンプレート

```text
このプロジェクトは【公開SEOサイト / ログインありWebアプリ】です。
主な要件は【要件】、ログインは【必要 / 不要】、メール送信は【必要 / 不要】です。
標準構成は【Astro / Vite + React + Hono + Clerk + Drizzle + Cloudflare Workers】。
DBは【D1 / Neon】を使います。選択理由は【理由】です。
未指定のサービス（Hyperdrive、Resend、キャッシュ、キュー等）は追加しないでください。
要件が標準構成を外れる場合は、実装前に理由と増える運用負荷を説明してください。
```

## 10. 具体的な推奨パターン例

### パターンA: SEO重視のコーポレートサイト

```text
Astro
静的生成または必要箇所のみサーバー生成
Cloudflare Pages/Workers系の配信
DB・認証・Resendなし（問い合わせを外部フォームに委譲する場合）
```

### パターンB: 小規模SaaSの最小構成

```text
Vite + React
Hono on Cloudflare Workers
Clerk
Drizzle
D1
Resendなし（Clerk標準メールで足りる場合）
Hyperdriveなし
```

### パターンC: SaaSの業務データが増えた構成

```text
Vite + React
Hono on Cloudflare Workers
Clerk（認証）+ アプリDB（認可・業務データ）
Drizzle + Neon
必要なトランザクションメールだけResend
Hyperdriveは接続数・遅延の実測後に判断
```

### パターンD: 公開コンテンツとアプリを分ける構成

```text
公開サイト: Astro（SEO、記事、ランディングページ）
アプリ: Vite + React + Hono（ログイン後の操作）
認証: Clerk
DB: 開始時の要件でD1またはNeonを選択。単純CRUDならD1
```
